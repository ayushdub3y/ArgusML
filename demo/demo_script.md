# ArgusML Demo Run-Sheet (§9)

This script provides step-by-step instructions for demonstrating the three core ArgusML dispute routing flows (Accept, Contest, Escalate) against test-mode webhooks.

---

## 1. One-Time Setup (Run Ahead of Pitch)

Execute once beforehand to ensure the trained Model A artifact and evaluation metrics are ready:

```bash
# 1. Train Model A and generate baseline metrics (DO NOT run live during pitch)
python -m src.model_a_adjudicator.train
python eval/run_eval.py
```

---

## 2. Live Demo Startup (Run During Pitch)

Seed the demo scenarios and start the webhook listener in the background:

```bash
# 1. Seed mock evidence for the 3 demo scenarios
python demo/seed_demo_evidence.py

# 2. Start the ArgusML webhook listener & operations dashboard (port 8080)
python src/webhook_listener.py &
```

---

## 3. Live Demo Dispute Flows

### Flow A: Auto-Accept Recommendation (Low p, Low V)
Simulates a dispute where fulfillment failed or evidence is missing, and the identity is under velocity thresholds. The engine recommends accept and generates a one-line reasoning card:

```bash
curl -s -X POST localhost:8080/webhook \
  -H 'Content-Type: application/json' \
  -d @demo/sample_accept.json
```
**Expected Response:** `{"status": "pending_human_accept", "dispute_id": "disp_demo_accept_001", "one_liner": "p=... V=₹230 ... recommend Accept"}`

---

### Flow B: High-Confidence Auto-Contest (High p, Positive EV)
Simulates an illegitimate claim where delivery OTP and courier POD are verified. The engine constructs a structured contest payload and triggers the Razorpay contest call:

```bash
curl -s -X POST localhost:8080/webhook \
  -H 'Content-Type: application/json' \
  -d @demo/sample_contest.json
```
**Expected Response:** `{"status": "contested", "dispute_id": "disp_demo_contest_001"}`

---

### Flow C: Velocity Loophole Mitigation & Human Escalation (§6b)
Simulates a dispute where the identity has breached rolling cumulative-exposure limits. The velocity gate intercepts the claim before the accept branch and routes it to human review:

```bash
curl -s -X POST localhost:8080/webhook \
  -H 'Content-Type: application/json' \
  -d @demo/sample_escalate.json
```
**Expected Response:** `{"status": "escalated", "dispute_id": "disp_demo_escalate_001"}`

---

### Step 4: Operations Dashboard Inspection
Verify the dashboard reflects the live states of pending checkpoints, escalations, and the audit trail:

```bash
curl -s localhost:8080/
```
Or open `http://localhost:8080/` in a browser to review the visual card interface.

## 4. Judge Q&A & Verbal Talking Points (§9, §11)

Prepare these concise verbal answers during the presentation and live Q&A:

### Q1: "Why is high-risk recall (84.3%) lower than overall recall (97.3%)?"
> **Verbal Answer:** *"RGNB cases tend to have sparser fulfillment evidence, so the model's confidence calibration is wider there — that's our top priority for post-hackathon targeted feature engineering."*

### Q2: "What is your biggest engineering catch or failure recovery?"
> **Verbal Answer:** *"Caught via test coverage: `respond_by` wasn't wired into the constructor, silently disabling the watchdog. We fixed it and locked in the behavior with dedicated regression tests."*

### Q3: "Why is your accept rate 37.8%? Isn't that conceding too many disputes?"
> **Verbal Answer:** *"The 37.8% accept rate reflects intentional expected-value (EV) triage. When $p \le 0.25$, contesting incurs a guaranteed ₹30 contest fee plus a ₹150 penalty risk if lost. Conceding low-probability or low-value claims avoids paying penalties on genuine customer complaints."*

### Q4: "Is this tested on real or synthetic data?"
> **Verbal Answer:** *"Evaluated on N=1,200 out-of-time holdout disputes generated by our seeded synthetic pipeline anchored to published UPI P2M distributions. We've documented this upfront in METRICS.md along with real-data validation roadmap steps in §5."*
